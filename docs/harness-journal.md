**Editor tools over MCP (2026-10-05, 0.0.7):** the bespoke `vscode_terminal` plugin tool is retired. The protocol handler is hand-rolled against the pinned MCP client 2.0 (read, not trusted: JSON responses accepted, 405 on the SSE probe tolerated, 404 on DELETE tolerated, notifications expect 202, and the client aborts unless `initialize` echoes a protocol version it offered, so the handler echoes). Zero npm dependencies, per the zero-dependency law. Tool calls publish a drain marker while executing, so a restart still waits for an in-flight editor build. The overlay emits the mount only when a control endpoint exists, so headless prepares compose a harness without editor tools instead of one dialing a dead port. `npm run bridge:check` now proves the real composition, not just the overlay text: real dsh resolves the generated preset child from the profile graph and dials the endpoint carrying the bearer header (`initialize x1, tools/list x1, unauthorized 0`). **Chromeless panel attempt and retirement (2026-10-05, 0.0.10 shipped, 0.0.11 retired):** the owner's complaint about the browser tab was exactly one address bar, and research says the built-in Browser area cannot hide it: every `browser.*` configuration key in the 1.140 workbench bundle was scraped, none hides the toolbar (`workbench.browser.showInTitleBar` only relocates it), and the deleted Simple Browser had an address bar too. A webview panel whose entire pane was an iframe of the harness URL shipped in 0.0.10 and died the same evening: the harness mints its browser session as an `HttpOnly; SameSite=Strict` cookie after the token redirect, and Chromium neither stores nor sends Strict cookies in a cross-site frame (an extension webview's document origin is never the harness origin). The iframe therefore only ever rendered the server's 401 body. The Browser area keeps working because it loads the page top-level, where the cookie applies. The panel mode is deleted in 0.0.11; do not re-propose iframe embedding unless upstream ships `Partitioned` cookies (see docs/upstream-issues.md; a loopback proxy that rewrites cookie attributes was considered and rejected as a permanent data-plane liability). **[Superseded 2026-11-07 — the panel shipped via a different mechanism: the session lives in a loopback proxy's cookie jar and never enters the webview at all; see the Chromeless panel era entry.]**

**Stale-tab sweep (2026-10-11, 0.0.16):** the owner's "the extension makes VS Code menus open behind the window" turned out to be a VS Code 1.140 bug with our tab as its trigger: the harness URL dies with every boot (fresh port and token by design), so a harness browser tab restored after a restart always fails to load, and a fail-load built-in Browser (a native Electron child view that composites above the window's DOM, `contentView.addChildView` in `out/mainImpl.js`) paints over every workbench menu. Owner reproduction: tab open across a restart equals dead menus; close the tab and the window is fine with the extension enabled; a successfully loaded tab never breaks. Z-order evidence: `EnumWindows` sampling during broken menus shows zero new OS windows from Code processes (menus are DOM; the native child view is invisible to top-level enumeration). `main.log`'s `[BrowserViewMainService] Failed to load initial URL` line from the poisoned session is the fingerprint. The bridge cannot prevent the restore, so it removes its own zombies: `Bridge.start` records every served URL in `vllmc/served-urls.log` (loopback-only, capped, `src/bridge/served-urls.ts`), activation sweeps editor tabs whose label equals a served `host:port`, keeps any whose origin still answers anything, and closes the rest by a bounded focus walk (no named-tab close command exists in 1.140: `workbench.action.closeTabs` is absent from every bundle chunk, verified), so the window's menus are usable seconds after boot. `dshBridge.sweepStaleTabs` is the manual recovery command. Tripwires: 89 vitest cases (history dedupe/cap/loopback rejection) and two new extension-host e2e tests (dead tab closes in 231 ms in a real VS Code, answering tab survives). Upstream draft for microsoft/vscode in `docs/upstream-issues.md` section 3, filing pending owner go; sibling closed report: microsoft/vscode#317715.

**Chromeless panel era: embed proxy, multi-view, per-chat titles, keyboard bridge (2026-11-07, squashed as 41d30de, vitest 96→105):** owner request: get rid of the browser address bar on the harness. Research: the built-in Browser area exposes no key that hides its toolbar (1.145 bundle scraped again), so the doors were panel, appWindow, or upstream. The 2026-10-05 no-iframe ruling stands as written — it rejected rewriting cookie attributes on the wire, a permanent data-plane liability — and what shipped is a different mechanism: `src/bridge/embed-proxy.ts` (zero dependencies, no vscode import) is a loopback proxy that OWNS the session: it rides the token login's 303 chain itself, keeps the `HttpOnly; SameSite=Strict` cookie in a server-side jar, injects it on every forwarded request and strips `Set-Cookie` from every response, so nothing the browser receives is stored or needed; the frame loads the page same-origin — a webview document's own origin is never the harness origin, so Strict is moot — while the panel CSP stays `default-src 'none'` plus frame-src the proxy plus its inline listener. `dsh-bridge.embedPort` (default 43171, EADDRINUSE falls back to ephemeral) gives the panel a URL that survives harness restarts: restart means retarget-and-reload the frame, the panel's own address never moves, which moots the 0.0.16/0.0.17 stale-tab bug class for the panel door (the zombie sweep stays for legacy Browser tabs). `openIn` gained `panel` (new default) and `appWindow` (spawns Edge/Chrome `--app=`, win32, with a visible fallback message chain); `embedded` and `external` remain.

Multi-view is honest because the harness session-multiplexes: `Open Another Harness View` (palette + a `+` in the panel title, `when: activeWebviewPanelId == 'dshBridge.harness'` — `webviewPanelId` does not exist in 1.145, certified against the bundle) opens a second full GUI with its own session selection; the status pill stays reveal-first by owner intent. `registerWebviewPanelSerializer` revives harness tabs after reloads — revived shells arrive empty, adoption fills them with the proxy frame the moment the harness URL is known. "Move into New Window" on a panel gives a free per-chat window (observed: the source window reloads on the move; the proxy re-grabs its port cleanly and the serializer heals the revived side); combined with `workbench.editor.showTabs: "multiple"` — which hides the tab strip exactly when one editor is open — a dedicated chromeless harness window needs zero code.
